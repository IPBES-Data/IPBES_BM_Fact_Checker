# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is an R/Quarto project for IPBES (Intergovernmental Science-Policy Platform on Biodiversity and Ecosystem Services) knowledge discovery. It uses the IPBES Linked Open Data (LOD) to extract the reference hierarchy from assessments, and snowball searching via the OpenAlex API to discover literature published after GA1 (2018).

**Scope (as of 2026-10-07).** `input/config.yaml` lists **one** live assessment, `GA1`. `VA`, `TCA`,
`IAS` and `BBA` are commented out under `collection.assessments:` and their fact-check output was
moved to `deep_archive/` on 2026-10-07. Commenting an assessment out there removes it from **every**
project, since that list is what the others filter; re-enabling one means uncommenting it **and**
adding it back to the relevant `reports:` entries, because `generate_report_wrappers()` hard-stops
when a report names an assessment the list does not have.

What is actually on disk for GA1:

| Stage | Coverage |
|---|---|
| `works_citing_parquet` | GA1 (the other four are archived, not deleted) |
| Phase 1 scores (`output/factchecker/claim_scores/`) | `granularity=atomic_bm`, `scorer_config=jev_atomic_bm`, both `keypaper=true` and `keypaper=false` |
| Phase 2 LLM (`output/factchecker/llm_verification/scores/`) | `llm_config=openrouter_cheap`, both keypaper values |
| `reports:` expansion | GA1 |

Two things worth holding onto. `fact_checking.configs.ga1_jev` carries `km: ["C."]`, so scoring is
scoped to one Key Message of four — narrowing scope computes less but never deletes what is out of
scope. And `nli_granularities` in `_targets_reporting.R` is a fixed literal
`c("naive_bm", "complete_bm", "atomic_bm")`, so reports render branches for granularities that have
no data; only `atomic_bm` is real.

**This branch (`Jev`) retired the `training` project on 2026-10-05 and the NLI scoring backend on
the same day.** Read `design_notes.md` before changing anything in the scoring chain: it holds the
measurements that motivated both, what they do and do not establish, and the proposed target
architecture. **Do not "clean up" `design_notes.md`** — it is the record of why the NLI was dropped,
and its NLI content is the point. The state before is the `NLI_dirty` branch.

## Build System

### Three targets projects, one repository

`_targets.yaml` defines the projects; each has its own script and its own store.

| Project | Script / store | Holds | Credentials |
|---|---|---|---|
| `collection` | `_targets_collection.R` / `_targets_collection/` | collection only: LOD → refs → zotero → works → snowball → works_citing (18 targets) | `API_openalex` |
| `factcheck` | `_targets_factcheck.R` / `_targets_factcheck/` | Phase 1 (Jev) → relevance screen → Phase 2 (LLM); **also** the gold standard (46 targets) | `API_openrouter` |
| `reporting` | `_targets_reporting.R` / `_targets_reporting/` | everything that renders (49 targets) | **none** |

```r
Sys.setenv(TAR_PROJECT = "collection");  targets::tar_make()
Sys.setenv(TAR_PROJECT = "factcheck");   targets::tar_make()
targets::tar_make(script = "_targets_reporting.R", store = "_targets_reporting")
```

**There is no `main` project and no `_targets.R`, deliberately.** A bare `tar_make()` fails with
"script does not exist" rather than silently running the one pipeline that re-downloads. The
project was renamed `main` → `collection` on 2026-10-07 and the store was **moved**
(`_targets/` → `_targets_collection/`), not recreated.

**Running the `collection` project is safe as of 2026-10-07.** It was not before: the
`output/` restructure edited a path literal inside every one of its builders, and since `targets`
hashes function bodies, all five download/network targets were queued to refetch a corpus that had
not changed — days of OpenAlex time, 16 GB of snowball deleted, and a different corpus from the one
every existing score was computed against.

The fix is **content-key guards** (`R/input_key_guard.R`), generalising what `download_ttls.R` has
always done with its GitHub blob SHA. Each expensive fetch records the set of identifiers that
actually determine its output and skips when that set is unchanged:

| target | key | cost if it runs |
|---|---|---|
| `ttl_path` | GitHub blob SHA | seconds |
| `refs_parquet`, `key_messages_parquet` | *(unguarded — local SPARQL)* | minutes |
| `zotero_parquet` | group id + Zotero `Last-Modified-Version` | minutes |
| `works_parquet` | the DOI set **and** the refs `(doi, km, bm)` mapping | hours |
| `snowball_parquet` | the seed work-id set | **days, 16 GB** |
| `works_citing_parquet` | *(unguarded — local DuckDB)* | minutes |

This is **not** an existence guard. "The directory is there, skip" breaks the invalidation contract
outright — a genuinely new TTL or Zotero item would be silently ignored, the bug class `0bb6bb0`
removed from two `nli_ready` builders. A content key keeps the contract: a real upstream change
moves the key and the fetch re-runs. Measured on GA1 — unchanged inputs skip in 0.24 s (works) and
0.06 s (snowball) with zero bytes touched; adding one DOI or one seed, or setting
`COLLECTION_FORCE_REFRESH=1`, correctly forces the fetch.

**The chain is a single line, not two independent roots.** Zotero is a second external service but
it sits *below* refs and takes only the group id from it
(`download_zotero.R`'s `infer_zotero_group_id()`), and the DOI set that drives OpenAlex comes from
`zotero_parquet`, not refs (`download_works.R`). So a new Zotero item cannot change `refs_parquet`;
it changes `works_parquet`, and from there the snowball.

```
ttl_path -> refs_parquet -> zotero_parquet -> works_parquet -> snowball_parquet -> works_citing_parquet
         -> key_messages_parquet
```

**The keys needed one-time seeding**, because the data on disk predates the mechanism and "no
recorded key" means refetch. `scripts/seed_collection_input_keys.R` (dry-run by default) asserts
that the outputs on disk correspond to the inputs on disk and records that. It deliberately does
**not** seed `zotero`: that key includes the live library version, and seeding it would assert
something the script cannot check — that the on-disk copy was downloaded at that version. Zotero
refetches instead, which is minutes, and if nothing changed the DOI set comes out identical and
`works` skips anyway.

**There were FOUR projects until 2026-10-05.** A `training` project held key papers → NLI → LLM →
training set → fine-tune → benchmark. It was retired when the model it existed to improve was
measured at or below chance at the job (AUC 0.50 for REFUTES, 0.38 for SUPPORTS, against
refutations confirmed by three independent reviewers) — see `design_notes.md` points 3 and 5-8, and
`input/reports/TD_NLI_training.qmd` for the design record. Two of its parts were never training and
moved into `factcheck`: the **key-paper QA chain** and the **gold standard**. Checkpoints and the
distilled training set are in `deep_archive/2026-10-05_training_dormant/`. Nothing is irreversible,
deliberately — every conclusion behind it comes from models judging models and the human review
round has not happened.

Each consumer declares the upstream outputs it reads as `format = "file"` targets **keeping the
producing project's target names**, so the moved targets work verbatim and a genuine upstream
change still invalidates downstream through content hashing.

**Cross-project state that no DAG describes** (named in `TD_targets.qmd`): the two append-only LLM
caches `output/factchecker/claim_completion/raw/` and
`output/factchecker/llm_verification/raw{,_keypaper}/`. The per-host lock directory that used to be
here went with the RunPod backend.

### Phase 1 is the Jev decisions API — there is no NLI backend on this branch

`score_one_claim_jev()` (`R/score_one_claim_jev.R`) POSTs to
`https://openrouter.ai/api/alpha/decisions` with three typed questions per pair — supports /
contradicts / bears-on-the-claim, defined in `input/prompts/jev_claim_questions.json` — and
cross-normalises the answers into `(p_supports, p_refutes, p_nei)`. That is the same operation the
retired zero-shot head performed with `passes: 3`, so the output schema, `uncertain_threshold`, the
`nli_route=` partitions and every report downstream are unchanged.

`_targets_factcheck.R` **hard-stops** on any `nli.configs.<name>` whose `backend:` is not `jev`.
There is no pod, no GPU, no host list and no pool health check — OpenRouter is a shared endpoint,
so there is nothing to be half-up; concurrency is per-request inside the scorer
(`httr2` `max_active`). `check_nli_pool_health()` and the RunPod machinery around it were **deleted**,
not unwired. `scripts/runpod/` went to `deep_archive/2026-10-07_runpod_pod_wrappers/` on 2026-10-07
because it read `nli.pod_defaults` and a config `pods:`/`image:` block that no longer exist, so it
could only die on its first lookup. `external/runpod/` is a **git submodule and must not be
committed** — it is untouched by any of this.

Several target names in `_targets_reporting.R` still read `nli_*` (`nli_overview_data`,
`nli_scores_qa_data`, `nli_bm_explorer_html`, `nli_granularities`, `nli_overview_figures`,
`nli_scores_qa_figures`). That is live naming, not a leftover file: the 2026-10-07 rename from
`nli_*` to `claim_*`/`scorer_*` covered `_targets_factcheck.R` only. The `nli:` key in
`config.yaml` and the `nli_route=` partition level are likewise still structural, read from a dozen
places in `R/`.

### Key papers are a partition level, not a parallel chain

`keypaper=<true|false>` is a hive partition **above** `assessment=` in all three fact-check trees.
keypaper = every paper tagged `relation == "keypaper"`; citing = citing **and not** keypaper, so
the two sets are disjoint by definition and need no de-duplication (70% of GA1's key papers do cite
another key paper, but `pro_snowball()` gives each node one relation tag with keypaper winning).

The placement above `assessment=` is load-bearing. `consolidate_claim_scores.R:96` globs with a
`$`-anchored `"/assessment=[^/]+/km=[^/]+/bm=[^/]+$"` regex; inserting a level between those three
would return `character(0)`, the consolidator would see zero on-disk groups, and its prune guard
would `stop()`. Above `assessment=`, the terminal three levels are untouched. It also gives each
side its own `disk_root` and `.scratch` root, which is what stops a citing branch and a keypaper
branch for the same claim racing on the same `<claim_id>.parquet` scratch file.

**Both phases are done** (2026-10-07). Phase 1 made `keypaper=` a partition level; phase 2 removed
the seven duplicate targets — `claim_work_pairs_keypaper`, `claim_units_keypaper{,_flat}`,
`claim_scores_keypaper{,_consolidated}`, `relevance_screen_keypaper`,
`llm_verification_keypaper_parquet`. **46 → 39 targets.** Each stage now handles both sides and
returns both roots, split by `claim_work_pairs_path()` / `claim_scores_consolidated_path()` /
`claim_relevance_path()` in `R/claim_chain.R` — always by the `keypaper=` level in the path, never
by position.

Units carry their own `keypaper` tag from `build_claim_units()`, and `score_one_claim_jev()`
defaults to the unit's tag rather than taking a literal, so one branch set covers both chains and no
branch can be sent to the wrong partition by a stale argument.

**The two Phase 2 builders are still separate functions**, called side by side with their own
explicit routing. The plan proposed merging them behind a conditional candidate filter —
`keypaper | (label %in% nli_labels & uncertain %in% allowed)` — and named that the single
highest-risk line in the change: wrong one way and key papers silently stop being reviewed, wrong
the other and 2.43M citing pairs go to full OpenRouter coverage. Calling the two functions with
explicit routing removes the duplicate target without ever writing that line.
`llm_verification_both()` asserts the routed count per side afterwards and warns loudly on zero, so
neither mistake can be silent. Merging the two functions is still worth doing — their real
duplication is a shared chunking/retry/cache/assembly loop — but that is a refactor of two large
functions, not a target-graph change.

What the duplication had already cost: `claim_scores_keypaper_consolidated` passed neither
`assessments=` nor `km=`, so its prune glob visited every group under the scorer root; and
`claim_units_keypaper` needed `km_scope` retro-fitted after the move out of the training project,
until which `km: ["C."]` scoped the citing works while silently scoring every key paper of every KM.

Note `_targets_reporting.R` still has targets *named* `claim_scores_keypaper{,_consolidated}` and
`llm_verification_keypaper_parquet`. Those are reporting's own `format = "file"` path declarations
and already point at the merged tree, but the names no longer mirror a producing factcheck target,
which is the one place the "keep the producing project's target names" convention is now broken.

### targets Pipeline (primary)

targets::tar_visnetwork()    # visualise dependency graph

**System dependency:** `fuseki-server` must be on `PATH` when `collection.sparql_url: fuseki`
(default). Install with `brew install fuseki`.

**Credentials:** read from the macOS keyring at startup via `keyring::key_get()`:

```r
keyring::key_set("API_openalex")      # collection
keyring::key_set("API_openrouter")    # factcheck
```

**What a `tar_make()` on `factcheck` can spend.** Three surfaces, none of them prompting first:

| Surface | Trigger | Cost |
|---|---|---|
| Jev decisions API | `claim_scores_by_claim`, `claim_scores_keypaper` | ~$0.00005/pair; ~$121 for GA1's 2.43M citing pairs, ~$1.50 for its 29,511 key-paper pairs |
| Relevance screen | `relevance_screen`, `relevance_screen_keypaper` | $0.0000172/pair, routed subset only |
| OpenRouter Phase 2 | `llm_verification_parquet`, `llm_verification_keypaper_parquet` | $0.000149/pair at `gpt-4o-mini` rates |
| Claim completion | `claim_work_pairs` under `granularity: atomic_bm` | per-token; usually a cache replay from `output/factchecker/claim_completion/raw/` |

Use `tar_make(names = ..., shortcut = TRUE)` to render reports against on-disk data without
triggering any of them.

**Running long `tar_make()` calls under tmux/SSH:** the `keyring::key_get()` calls need macOS
Keychain access every time the script is sourced, including inside whatever process runs the
pipeline. From a terminal session with no path to the GUI/WindowServer (SSH into the Mac — even to
yourself — is enough; tmux inherits whatever its parent has), a Keychain prompt can't be shown and
`tar_make()` fails with `keyring error (macOS Keychain), cannot get password: User interaction is
not allowed`. This is a session/display-access issue, not a `callr` one — `callr_function = NULL`
does not fix it. Before starting a long background run:

1. `security unlock-keychain ~/Library/Keychains/login.keychain-db` in that same terminal.
2. If it still fails, the per-app access-confirmation dialog needs approving from a real GUI
   session (physically at the machine, or Screen Sharing) — Keychain Access.app, find
   `API_openalex`/`API_openrouter`, *Get Info* → *Access Control* → **Allow all applications**.
3. Last resort for one run: `export API_openrouter=<key>` in the shell *before* launching R.

**Not wired into any pipeline (source files exist but no active target):** `R/build_fulltext.R`,
`R/resolve_citations.R`, `R/write_sections_parquet.R`. Their outputs are no longer produced.
`sections_parquet`/`sections_sparql` were **disabled 2026-09-15**: nothing consumed them — no target
took `sections_parquet` as an argument and no qmd read the dataset; its only ever consumer was
`resolve_citations.R`, itself long orphaned — so it paid a SPARQL extraction plus Fuseki round trip
per assessment on every rebuild for output nothing read. `queries/sections.sparql` remains, so
re-enabling is uncommenting the block in `_targets_collection.R`.

**Parked: the original per-sentence scoring chain.** `nli_ready_parquet`, `nli_claim_units` and
`nli_claim_units_flat` are **commented out**, alongside their already-commented consumer
`nli_scores_by_claim`. Nothing consumes them and `output/factchecker/claim_work_pairs/` does not exist, so carrying
them into `_targets_factcheck.R` would have built a second large cross-join for output no active
target reads. Everything downstream reads the evidence chain. They are kept because NEXT_STEPS.md
documents the evidence segmentation as a parallel *second* approach "not a replacement".

### Diagrams

`R/render_diagrams.R` renders Mermaid `.mmd` sources to SVG. There are two families.

**Hand-authored, one per project** — `input/mmd/workflow_collection.mmd`,
`workflow_factcheck.mmd`, `workflow_reporting.mmd`, plus `overview.mmd`, which is not a pipeline
picture but the price ladder: which model runs at which step and what it costs. All four were
rewritten on 2026-10-07 to drop the retired NLI backend; `workflow_factcheck.mmd` also absorbed the
key-paper chain, which is now a `keypaper=` partition rather than a parallel set of nodes. Node ids
are shared where a consumer diagram shows something collection produces. **A comment line
containing only `%%` is not an empty comment to mermaid** — it renders as a visible stray node, so
bare separator lines are written `%% --`.

**Auto-generated from the live DAG** — `build_pipeline_mmd()` calls `tar_mermaid()` and so renders
**whatever project it is run inside**: `_targets_collection.R` writes `pipeline_collection.mmd`,
`_targets_factcheck.R` writes `pipeline_factcheck.mmd`, `_targets_reporting.R` writes
`pipeline_reporting.mmd`. The self-exclusion list (so a pipeline picture never depicts the targets
that draw it) is derived **by pattern from the live manifest**, not hardcoded — a fixed list
silently stops excluding anything the moment a target is renamed.

**Its dependency is the project's own `_targets_*.R`, not the `R/` listing.** The `targets_script`
target replaced `r_files` on 2026-10-07. `r_files` was wrong in both directions and measurably so:
too sensitive, because an edit to any of ~60 files redrew a byte-identical picture; and not
sensitive enough, because `targets` does not track the pipeline script as a dependency of the
targets it defines, so adding, removing or renaming a target left the diagram untouched. Both
symptoms were on disk — `pipeline_factcheck.mmd` still named `nli_ready_evidence_parquet` and
`nli_scores_by_claim_evidence` long after the rename to `claim_*`, and `pipeline_reporting.mmd` held
a byte-identical copy of **collection's** graph with not one reporting target in it. The graph can
only change when the script does, because `tar_mermaid(targets_only = TRUE)` draws target-to-target
edges taken from each target's command expression; a function body in `R/` cannot move an edge.
Collection's version additionally pointed at `_targets.R`, a path that no longer exists.

### Quarto Report

**One Quarto project.** `input/reports/` → `output/reports/`, rendered by `reports_project` +
`report_fact_checker`: the main report, the six `TD_*.qmd`, and the generated wrappers.

**There were two until 2026-10-05.** `input/reports_training/` held three QA reports the `training`
project rendered itself, because a Quarto project has exactly one `output-dir` and a single-file
render picks up a project's `format:` but not its `output-dir`. That project is retired; two of its
reports are deleted and the third (`_QA_NLI_Benchmark_Report.qmd`) is **parked** —
underscore-prefixed, so Quarto excludes it from the project entirely, and renaming it back is all
that is needed. Its metrics (Cohen's κ against human labels, the R1/R2 ceiling, bootstrap CIs,
inverse-probability weighting) are still wanted; its subject — fine-tuned checkpoints against a
zero-shot baseline — is not. `report_project_dirs()` is back to one directory, kept as a
one-element vector so adding a second is adding an element.

**`TD_NLI_training.qmd` stays in `input/reports/`** despite being a training design document: the
main report links to it via `td_doc_link()`, and TD docs are one family and live together. Like
`design_notes.md`, it is a **record** — its NLI content is deliberate.

Three targets cover all ~34 documents, replacing **nineteen** former ones:

| Target | Renders |
|---|---|
| `reports_project` | `tar_quarto(path = "input/reports")` — the generated wrapper documents plus the `TD_*.qmd` design docs |
| `report_fact_checker` | `tar_quarto(path = "input/reports/IPBES_Fact_Checker.qmd")` — the main report, deliberately excluded from the project's `render:` list so it runs **after** the rest, since it links to and copies in their rendered html. **Its html lands in `input/reports/`, not `output-dir`** — Quarto applies a project's `output-dir` only to files it renders *as part of* the project. `build_report_output_dir()` copies it (plus its `_files/` sidecar, which matters because this is the only report with `embed-resources: false`) into `output/reports/`. Two workarounds were tried and rejected by direct test: `quarto render <file> --output-dir` is refused outright ("can only be used when rendering projects"), and re-listing the file after the exclusion in `render:` does not re-include it. Note also that a project render **deletes** a stray `IPBES_Fact_Checker.html` from `input/reports/`, so `reports_project` must run first, which the qmd's own `tar_read(reports_project)` guarantees |
| `report_output_dir` | no rendering — the deploy extras (`.nojekyll`, `index.html`, `CLAUDE.md`) plus the copy of `IPBES_Fact_Checker.html` and its sidecar out of `input/reports/` |
| `report` | no rendering — a single entry point depending on all three. **`shortcut = TRUE` does not work with it**: shortcut builds only the named target and loads its dependencies from the store, so nothing re-renders. Name the three explicitly instead |

**Why this replaced the old design.** `tar_quarto()` derives each report's dependencies from the
`tar_read()` calls in the project's sources, so they no longer have to be listed by hand. The old
`report_fact_checker` listed eight bare symbols and **missed five** dependencies the qmd genuinely
reads. `output-dir: ../../output/reports` also removes a `file.rename()` step and with it the
stale-`_files/libs/` bug.

**Parameterized reports are generated, not parameterized at render time.** Quarto renders each
`.qmd` in a project exactly once, so the families that used to be one source rendered N times with
different `execute_params` are now one **shared body** (`_<name>_body.qmd`) plus one tiny
**generated wrapper** per combination. The wrapper's *filename is the output filename*, so no
`output_file` plumbing exists anywhere. Two non-obvious constraints shape that design:

1. **Generation runs in the script's preamble, not in a target.** `tar_quarto()` resolves the
   project's file list *and* its dependency edges when the script is **sourced**, baking both into
   the target's command. A wrapper produced by an upstream target would contribute nothing on the
   run that created it.
2. **The `tar_read()` calls live in the wrapper, not the body.** Quarto excludes underscore-prefixed
   files from the project completely, so a body is never scanned for dependencies. Each wrapper
   declares its own literally and hands the values to the body as a `report_deps` list.

**Adding or changing a report is a `config.yaml` edit.** Each `reports:` entry names a `qmd_name`,
a `title` template, and the dimension(s) to expand over. `label` is always derived
(`REFUTES`/`SUPPORTS`). Omitted dimensions are derived, notably `nli_config` via
`nli_config_for_granularity()` — the safe default, since naming the wrong config silently makes
already-scored data look unscored. Generated wrappers are gitignored; `_quarto.yml` and the
`_*_body.qmd` files are the real sources.

**Known gap: nothing prunes stale output.** Quarto's project render was measured **not** to remove
files it does not manage, so html from an earlier naming convention persists in `output/reports/`
until removed by hand. **The same gap covers `output/reporting/tables/` and `figures/`, and always
has.** Several naming generations of the funnel rds files coexist there, accumulated as the selected
config moved from `deberta_zeroshot` to `bge_m3_zeroshot_*` to `jev_atomic_bm` and as
`granularity_suffix()` became unconditional. Only the name matching the current
`(scorer_config, granularity)` pair is live; the rest are orphans that no target reads and no target
deletes. When judging whether something "has been built", check the filename against the *current*
suffix convention rather than trusting that a plausible-looking file on disk is current.

**Manual rendering needs `--execute-dir "$(pwd)"`.** Quarto executes in the document's own
directory by default, which breaks both `tar_read()` and the relative `output/reports` paths the
qmds use; `tar_quarto()` passes `execute_dir = getwd()` for you.

## Architecture

### Output layout

`output/` is split by producing project, matching `_targets.yaml`. This was done on 2026-10-07 by
moving directories, not by re-running anything.

```
output/collection/     LoD, refs, key_messages, zotero, works, snowball,
                       works_citing, works_citing_meta            (19 GB)
output/factchecker/    claim_work_pairs, claim_scores, claim_completion,
                       llm_candidate_scope, llm_relevance,
                       llm_verification                           (13 GB)
output/reporting/      figures, tables                            (2.2 GB)
output/reports/        rendered html — TRACKED, published to Pages (136 MB)
```

### targets Pipeline Data Flow

```
input/config.yaml
  collection:
    → output/collection/LoD/<id>.ttl
    → output/collection/refs/assessment=<id>/
    → output/collection/key_messages/assessment=<id>/
    → output/collection/zotero/assessment=<id>/
    → output/collection/works/assessment=<id>/km=<km>/bm=<bm>/
    → output/collection/snowball/{nodes,edges,keypaper}/assessment=<id>/
    → output/collection/works_citing/assessment=<id>/          (slim km/bm/id mapping)
    → output/collection/works_citing_meta/assessment=<id>/     (one row per distinct work)

  factcheck:
    → output/factchecker/claim_work_pairs/granularity=<g>/keypaper=<t|f>/assessment=<id>/km=<km>/bm=<bm>/
    → output/factchecker/claim_scores/granularity=<g>/scorer_config=<cfg>/keypaper=<t|f>/assessment=<id>/km=<km>/bm=<bm>/
    → output/factchecker/llm_candidate_scope/assessment=<id>/km=<km>/bm=<bm>/
    → output/factchecker/llm_relevance/assessment=<id>/keypaper=<t|f>/
    → output/factchecker/llm_verification/scores/llm_config=<cfg>/keypaper=<t|f>/assessment=<id>/nli_route=<route>/km=<km>/bm=<bm>/
    → output/factchecker/claim_completion/raw/model=<m>/prompt=<hash>/
    → output/factchecker/llm_verification/raw{,_keypaper}/model=<m>/prompt=<hash>/assessment=<id>/

  reporting:
    → output/reporting/tables/, output/reporting/figures/
    → output/reports/   (rendered html, tracked)
```

**Active Phase 1 — Jev** (`TD_BM_NLI_approach.qmd` for the segmentation design):
`claim_scores_by_claim` classifies each work against its partition's Background Message as
SUPPORTS / REFUTES / NOT_ENOUGH_INFO. Premise = cleaned `title`+`abstract`; hypothesis = one BM
claim. The full probability distribution is stored; all thresholding is done downstream in `dplyr`.

**Relevance screen** (`R/build_llm_relevance_screen.R`) sits between the phases and **scores
without filtering** — `fact_checking.relevance_screen.threshold` is `~`. See that file's row below;
its current scores are chunk-level, not per-paper, which is a known defect.

**Active Phase 2 — LLM verification** (`TD_NLI_LLM_two_phase.qmd`): `llm_verification_parquet`
reviews only the pairs flagged `REFUTES` or `SUPPORTS` and `certain`, one
`ellmer::chat_openrouter()` call per `(claim, work)` pair, with a resumable per-pair cache and a
post-hoc check that demotes any verdict whose cited quote isn't actually verbatim in the supplied
text. Key papers (`keypaper=true`) are reviewed at **full coverage**, no routing — a small, bounded,
high-importance set. Every citing work under a claim's BM is reviewed (an earlier
`subset: "all"`/`"default"` mechanism was retired once real GA1 atomic_bm data showed the narrowing
reduced routed pairs by only ~14%). Instead each reviewed pair is tagged `direct_evidence_match`.

The `collection.sparql_url` key controls the SPARQL backend:
- `"fuseki"` — each parquet builder starts an in-memory Fuseki session on a deterministic port and
  POSTs the assessment's TTL into the named graph returned by `assessment_graph_iri(id)`
- Any URL — the parquet builders query that endpoint directly; no Fuseki lifecycle needed

Config is split into fine-grained targets so that changing one entry does not invalidate others.
Each top-level config key maps to its own intermediate target; `nli:` and `llm_verification:` are
**libraries of named `configs`** that select nothing themselves — see *Purpose blocks* below.

**Per-assessment named graphs:** all SPARQL queries wrap their patterns in
`GRAPH <%GRAPH_IRI%> { ... }`. The placeholder is substituted at query time by
`read_sparql_query()` in [R/extract_lod.R](R/extract_lod.R) using `assessment_graph_iri()` from
[R/branch_helpers.R](R/branch_helpers.R) (currently `http://ontology.ipbes.net/report/<id>`). The
same code path works against local Fuseki and a shared IPBES endpoint hosting all assessments under
the same IRI convention. If IPBES adopts a different convention, edit `assessment_graph_iri()` in
one place.

### Key Design Patterns

- **targets caching**: each target is re-run only when its inputs change. Note `targets` hashes
  **function bodies**, so editing a path literal inside a builder invalidates its target — which is
  exactly what the `output/` restructure did to all of `collection`.
- **Purpose blocks**: `input/config.yaml` keeps `nli:` and `llm_verification:` as *libraries of
  named definitions* and puts the **selection** in a per-purpose block. `fact_checking:` is itself a
  library plus an `active:` selection, so several whole configurations can be written down and one
  selected. A config may also carry **`km:`**, scoping scoring to named Key Messages; **omitting it
  means all**. The strings are per-assessment and inconsistent (`A.` in GA1, `KM-A1` in IAS, `KM1`
  in VA/TCA/BBA), matched literally, and validated inside `build_claim_units()` rather than in
  config — KMs live in `key_messages_parquet`, a target, so config cannot check them, and `"A"` for
  `"A."` would otherwise enumerate zero claims and look like a successful no-op. The filter operates
  on the **`(km, bm)` pair**: outside GA1 a BM sits under several KMs, so filtering on `km` alone
  would let a shared BM leak in everywhere. **Narrowing scope computes less; it never deletes what
  is out of scope.** That required making three stages additive — `consolidate_claim_scores()`,
  `build_llm_relevance_screen()` and `build_llm_verification_parquet()` — each of which used to wipe
  its whole output subtree before writing. There is no global `active:`. Resolved and **validated**
  by `purpose_config()` (`R/branch_helpers.R`) — naming a config that isn't in the library is a hard
  error, because it would otherwise read as "nothing scored yet" and re-dispatch a corpus at real
  cost. Scope lives here rather than as per-assessment flags inside `assessments:`, which would
  change `assessments_list`'s value and invalidate everything downstream.
- **Read `assessments:` through `config_assessments()`** (`R/branch_helpers.R`), never by reaching
  into the structure. It moved under `collection:` on 2026-10-07 and was accessed from six places; a
  silent `NULL` there reads as "no assessments" — every branched target produces nothing, which
  looks like a successful empty run rather than a broken config. The helper stops with a message
  naming the move.
- **Fine-grained config**: `config` is split into `sparql_url`, `workers`, `assessments_list`,
  `scorer_name`/`scorer_config`/`scorer_configs_all`, `granularity`, `max_length`,
  `claim_completion_model`, and `llm_verification_active`/`llm_verification_config` so unrelated
  config sections don't cascade invalidation. `granularity` and `max_length` are both read out of
  *the active scorer config*, so changing the purpose block's `nli:` invalidates them together.
- **Fuseki lifecycle**: started and stopped inside the parquet builders; cleanup is idempotent and
  handled by `on.exit()`.
- **Assessment branching**: `assessment` is the branch key, so adding a new assessment only computes
  the new branch.
- **Parquet databases**: queried lazily with `arrow::open_dataset()` + `dplyr` verbs, collected into
  memory only when needed. ⚠ **`open_dataset()` on a list of files loses hive partition columns** —
  open the directory, or re-attach the columns from the path segments.
  `build_llm_relevance_screen.R:359-365` documents this trap; it has been hit repeatedly.
- **SPARQL queries as files**: tracked as `format = "file"` targets (`refs_sparql`,
  `key_messages_sparql`) — editing a query file invalidates only its downstream parquet target.
- **Legacy QMD caching**: uses `file.exists(fn)` checks. Delete the relevant `.rds` or parquet
  directory to force recomputation.

### Shiny App — removed 2026-10-05

`shiny_app/` was a pure read layer over `output/` — `app.R` plus ten modules,
~1,300 lines, no target, never part of `reports_project`. Deleted on the `Jev`
branch. Verified before removal that **no function in `R/` was used only by it**,
so nothing else had to change.

Two ideas in it are worth remembering if anything like it is rebuilt. Its
dropdowns were populated by scanning `output/` at startup, **never from
`input/config.yaml`**, because the set of `(assessment × granularity ×
nli_config × llm_config)` combinations actually built is incomplete and
inconsistent with the config. And artifacts written under older naming
conventions were surfaced as `granularity = "unspecified"` rather than dropped,
so the app was the one place that showed the stale-output situation described
under *Quarto Report* instead of papering over it.

### Terminology

- **KM** = Key Message (e.g. `"A."`)
- **BM** = Background Message (e.g. `"A1"`)
- **SM** = Sub-Message
- **LOD** = Linked Open Data — IPBES assessments in RDF/Turtle format
- **key papers** = GA1 references used as snowball seeds (`oa_input == TRUE` in QMD nodes)
- **non-key papers** = papers discovered via snowball (`oa_input == FALSE`)
