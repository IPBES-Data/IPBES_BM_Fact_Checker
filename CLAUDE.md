# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is an R/Quarto project for IPBES (Intergovernmental Science-Policy Platform on Biodiversity and Ecosystem Services) knowledge discovery. It uses the IPBES Linked Open Data (LOD) to extract the reference hierarchy from assessments, and snowball searching via the OpenAlex API to discover literature published after GA1 (2018).

**Scope (as of 2026-10-05).** `input/config.yaml` lists **five** assessments — `GA1`, `VA`, `TCA`,
`IAS`, `BBA` — but coverage per stage is deliberately uneven, and **the config is not a guide to
what exists**. What is actually on disk:

| Stage | Assessments with data |
|---|---|
| `works_citing_parquet` | GA1, VA, TCA, IAS, BBA (all five) |
| Phase 1 NLI, citing works (`output/nli_scores_evidence/`) | GA1, IAS — under `atomic_bm` and `complete_bm` only |
| Phase 2 LLM, citing works (`output/llm_verification/scores/`) | GA1 only |
| Phase 2 LLM, key papers (`output/llm_verification/scores_keypaper/`) | GA1, VA, TCA, IAS |
| Phase 1 NLI, citing works under the **fine-tune** (`nli_config=bge_m3_ft_ga1`) | GA1, **KM C. only** |
| `reports:` expansion | GA1, IAS |

Two consequences worth holding onto: **no `naive_bm` scores exist at all** despite config comments
still calling it “the current default corpus” and `nli_granularities` rendering a report branch for
it; and the key-paper QA chain has run for assessments whose citing-works chain has not, which is
exactly the case `build_nli_training_data()` was built to tolerate (it survives as a hand-run
utility; see the removed-files row below). Several
measured figures quoted later (file counts, dataset sizes) date from when the config listed four
assessments; they are kept as-measured and flagged where that matters. Adding an assessment means
editing **both** `assessments:` and the relevant `reports:` entries.

**This branch (`Jev`) retired the `training` project on 2026-10-05.** Read
`design_notes.md` before changing anything in the scoring chain: it holds the
measurements that motivated it, what they do and do not establish, and the
proposed target architecture. The state before is the `NLI_dirty` branch.

## Build System

### Several targets projects, one repository

`_targets.yaml` defines the projects; each has its own script and its own store.
The split is in progress — see `TD_targets.qmd` for the design and the
remaining steps.

| Project | Script / store | Holds | Credentials |
|---|---|---|---|
| `main` | `_targets.R` / `_targets/` | collection only: LOD → refs → zotero → works → snowball → works_citing | `API_openalex` |
| `factcheck` | `_targets_factcheck.R` / `_targets_factcheck/` | citing works → NLI (Phase 1) → LLM verification (Phase 2); **also** the key-paper QA chain and the **gold standard** | `API_openrouter` |
| `reporting` | `_targets_reporting.R` / `_targets_reporting/` | everything else that renders | **none** |

```r
targets::tar_make()                                   # main (the default)
Sys.setenv(TAR_PROJECT = "factcheck"); targets::tar_make()
targets::tar_make(script = "_targets_reporting.R", store = "_targets_reporting")
```

**There were FOUR projects until 2026-10-05.** A `training` project held key
papers → NLI → LLM → training set → fine-tune → benchmark. It was retired when
the model it existed to improve was measured at or below chance at the job
(AUC 0.50 for REFUTES, 0.38 for SUPPORTS, against refutations confirmed by three
independent reviewers) — see `design_notes.md` points 3 and 5-8, and
`input/reports/TD_NLI_training.qmd` for the design record. Two of its parts were
never training and moved into `factcheck`: the **key-paper QA chain** and the
**gold standard**. Checkpoints and the distilled training set are in
`deep_archive/2026-10-05_training_dormant/`; the state before is the `NLI_dirty`
branch. Nothing is irreversible, deliberately — every conclusion behind it comes
from models judging models and the human review round has not happened.

Each consumer declares the upstream outputs it reads as `format = "file"`
targets **keeping the producing project's target names**, so the moved targets
work verbatim and a genuine upstream change still invalidates downstream
through content hashing. One exception, in `reporting` and deliberate: `output/nli_ready_evidence`
(163 GB) is passed as a plain untracked path string, because hashing it on every
check would make the one project whose appeal is being fast and free slower than
the scoring it reports on. `output/nli_training_finetuned` (76 GB) was the
second until the training project was retired; it is now in `deep_archive/`.

**`main` keeps the original store deliberately.** A fresh store makes every
target outdated by definition, and `download_works()` `unlink()`s its output
before refetching while `build_snowball_parquet()` has no existence check at
all — re-running them would cost days of OpenAlex time *and* produce a
different corpus from the one every existing score was computed against. So
targets are *deleted from* `_targets.R` as they move out; its metadata survives
untouched. Do **not** run `tar_prune()` mid-migration: orphaned metadata for
removed targets is harmless (`targets` ignores rows for targets not in the
pipeline) and keeps a rollback available.

**A fresh consumer store makes even a no-op pass do work.** Both scoring chains
depend on `nli_pool_health`, which fails hard if any host in the active config
is unreachable — so a run that will delta-skip every claim still needs a live
pool first. One pod in the active config's `host:` list satisfies it.

**`factcheck`'s first run pays a one-time 163 GB rebuild.** A fresh store makes
`nli_ready_evidence_parquet` outdated by definition, and `0bb6bb0` removed its
early return, so the `atomic_bm` cross-join is rebuilt from its real inputs —
hours of local compute, no money. The output already on disk is not endangered;
the rebuild reproduces it. Start it from a quiet point.

**The gold standard is still a hard gate, but on less.** `goldstandard` lives in
`_targets_factcheck.R` now and `stop()`s until `input/goldstandard/R{1,2}_<assessment>.csv`
are filled in. The two targets it used to gate — `nli_finetuned_model` and
`nli_benchmark_qa_data` — are gone, so today it gates nothing automatically. It
is kept because it is the only thing that can test the decision that removed
them. The chain was: build `nli_training_data` (defines the three folds) → run
`build_goldstandard_sample()` **by hand** → two reviewers fill the generated
templates → commit. `R/build_nli_training_data.R` survives as a hand-run utility
(not a target) precisely because `build_goldstandard_sample()` needs it to find
the holdout fold.

**Cross-project state that no DAG describes** (named in
`TD_targets.qmd`): the per-host lock directory
`output/nli_scores/.locks/`, shared by both scoring projects (deliberate — one
pool, one queue), and the two append-only LLM caches
`output/claim_completion/raw/` and `output/llm_verification/raw*/`.

### targets Pipeline (primary)

```r
targets::tar_make()          # run all outdated targets
targets::tar_visnetwork()    # visualise dependency graph
targets::tar_outdated()      # list what needs re-running
```

**System dependency:** `fuseki-server` must be on `PATH` when `sparql_url: fuseki` (default). Install with `brew install fuseki`.

**Credentials:** `_targets.R` reads `API_openalex` and `API_openrouter` from the macOS keyring at startup via `keyring::key_get()`. Set them before running `tar_make()`:

```r
keyring::key_set("API_openalex")
keyring::key_set("API_openrouter")
```

**What a bare `tar_make()` can spend.** Four independent surfaces, all reachable transitively from
`report_fact_checker`, none of them prompting first:

| Surface | Trigger | Cost |
|---|---|---|
| RunPod NLI pool | `nli_scores_by_claim_evidence`, `nli_scores_keypaper_evidence` | GPU hours; millions of pairs |
| OpenRouter Phase 2 | `llm_verification_parquet`, `llm_verification_keypaper_parquet` | per-token, ~$7.75 for the 52k `SUPPORTS` backlog at `gpt-4o-mini` rates |
| Claim completion | `nli_ready_evidence_parquet` under `granularity: atomic_bm` | per-token; usually a cache replay from `output/claim_completion/raw/` |

Use `tar_make(names = ..., shortcut = TRUE)` to render reports against on-disk data without
triggering any of them. The fourth surface, local fine-tuning, is gone with the `training` project.

**Running long `tar_make()` calls (e.g. `llm_verification_parquet`, `llm_verification_keypaper_parquet`) under tmux/SSH:** the `keyring::key_get()` calls above need macOS Keychain access every time `_targets.R` is sourced, including inside whatever process actually runs the pipeline. From a terminal session with no path to the GUI/WindowServer (SSH into the Mac — even to yourself — is enough to lose this, tmux inherits whatever its parent session has), a Keychain access prompt can't be shown and `tar_make()` fails outright with `keyring error (macOS Keychain), cannot get password: User interaction is not allowed`. This is a session/display-access issue, not a `callr`-subprocess one — passing `callr_function = NULL` does not fix it. Before starting a long background run this way:
1. `security unlock-keychain ~/Library/Keychains/login.keychain-db` in that same terminal (prompts for your login password there, no GUI needed).
2. If it still fails, the per-app access-confirmation dialog itself needs approving from an actual GUI session (physically at the machine, or Screen Sharing) — open Keychain Access.app, find `API_openalex`/`API_openrouter`, *Get Info* → *Access Control* → **Allow all applications** (or add the R binary and set **Always Allow**). Once granted, it persists across future headless/tmux runs.
3. As a last resort for one run, bypass keyring entirely: `export API_openrouter=<key>` in the shell *before* launching R, so `_targets.R`'s own `Sys.setenv(... = keyring::key_get(...))` line still runs but you've confirmed Keychain access via step 1/2 first — or comment that line out temporarily and rely on the exported env var alone.

**Not wired into `_targets.R` (source files exist but no active target):** `R/build_fulltext.R`, `R/resolve_citations.R`, `R/write_sections_parquet.R`. Their corresponding outputs (`output/fulltext/`, `output/resolved_sections/`, `output/sections/`) are no longer produced by the live pipeline. `sections_parquet`/`sections_sparql` were **disabled 2026-09-15** (commented out in `_targets.R`, `output/sections/` deleted): nothing consumed them — no target took `sections_parquet` as an argument and no qmd read the dataset; its only ever consumer was `resolve_citations.R`, itself long orphaned — so it was paying a SPARQL extraction plus Fuseki round trip per assessment on every rebuild for output nothing read. `R/write_sections_parquet.R` and `queries/sections.sparql` both remain, so re-enabling is uncommenting the block in `_targets.R`.

**Parked: the original per-sentence scoring chain.** `nli_ready_parquet`, `nli_claim_units` and `nli_claim_units_flat` are now **commented out** in `_targets.R`, alongside their already-commented consumer `nli_scores_by_claim`. They were parked rather than carried into `_targets_factcheck.R` during the split: nothing consumes them, `output/nli_scores/` is 0 B and `output/nli_ready/` does not exist at all, so a fresh factcheck store would have built a second large cross-join for output no active target reads. Everything downstream reads the evidence chain (`nli_scores_by_claim_evidence` → `output/nli_scores_evidence/`). `R/build_nli_ready_parquet.R`, `R/build_nli_claim_units.R` and the three targets are kept because NEXT_STEPS.md documents the evidence segmentation as a parallel *second* approach “not a replacement”, so the two can be scored and compared side by side — not because anything consumes them today. (Note `TD_BM_NLI_approach.qmd` does **not** cover the per-sentence arm at all; NEXT_STEPS.md is its only design record.) Reviving the arm means moving the parked block into `_targets_factcheck.R` (which already has every target it needs) and uncommenting `nli_scores_by_claim`, which dispatches the whole per-sentence corpus at real GPU cost — see `R/build_nli_overview_data.R`'s row below for why that target is deliberately pointed at the evidence chain.

### Pod lifecycle (`scripts/runpod/`)

`input/config.yaml` is the only place a pod pool is described. Two wrappers around
the `external/runpod` submodule's own `create_pods.sh`/`stop_pods.sh` read it:

```bash
export RUNPOD_API_KEY=...
scripts/runpod/start_nli_pods.sh         # pods.count from config; -n overrides
scripts/runpod/stop_nli_pods.sh          # -d to delete rather than stop
```

Both take **`-p/--purpose`** (`fact_checking`, the default, or `training`). It is
not cosmetic: the two purposes deliberately run **different models** — fact
checking on the fine-tune, training left on zero-shot so the training set is not
distilled from labels the model itself shaped — so a single wrapper that only
ever resolved `fact_checking` could not start training's pool at all, and the
obvious workaround (point training at whatever pool happens to be up) scores key
papers with the wrong model under the right `nli_config=` name. That is why
`bge_m3_zeroshot_atomic_bm` now carries `expect_model:` — the two models differ
by `passes: 1` vs `3`, a different scoring scheme entirely, and the plain `model:`
check is only a warning.

`start_nli_pods.sh` resolves the chosen purpose's `nli:` name, merges
`nli.pod_defaults` with that config's own `image:` and `pods:` block into
`output/config/runpod_nli_<ACTIVE>.conf`, launches, and writes the resulting
hostnames back into that config's `host:`. The `.conf` is **disposable** —
regenerated on every run, uncommented, never edited by hand. The hand-written
`input/nli_pods_*.conf` files are kept for reference and read by nothing; their
comments had already drifted (both name `nli.configs.*` keys that no longer
exist).

**`NLI_MAX_LENGTH` is derived from the config's `max_length`, never restated** —
a `pods.extra_env.NLI_MAX_LENGTH` that contradicts it is a hard error. Serving a
512-trained model at 2048 raises nothing at all and merely scores worse (the
near-miss `a8c6ea4` records), so this removes the mismatch by construction
instead of detecting it afterwards.

**The write-back into `config.yaml` is a surgical single-line replacement**, done
by `scripts/runpod/nli_pods.R` (R, because the one comment-preserving YAML tool,
`yq`, is not installed here, and the edit needs to *parse* its own result before
trusting it). 342 of `config.yaml`'s lines are comments carrying this project's
design rationale and a YAML round-trip would erase every one. Four guards, all
abort-and-leave-untouched: write to a temp file; it must parse; the parsed result
must be identical to the original except `nli.configs.<active>.host`; `diff` must
show exactly one changed line. `stop_nli_pods.sh` leaves `host:` **alone** — a
stopped pod resumes under the same hostname. A short pool is written back with a
loud warning naming requested vs ready: a partial pool scores more slowly, not
wrongly, since `score_one_claim()` dispatches per free host. Both scripts honour
`NLI_CREATE_PODS`/`NLI_STOP_PODS` to point at a stub, which is how they are
tested without spending money.

### Quarto Report

**One Quarto project.** `input/reports/` → `output/reports/`, rendered by
`reports_project` + `report_fact_checker`: the main report, the six `TD_*.qmd`,
and the generated wrappers.

**There were two until 2026-10-05.** `input/reports_training/` →
`output/reports_training/` held three QA reports the `training` project rendered
itself, because a Quarto project has exactly one `output-dir` and a single-file
render picks up a project's `format:` but not its `output-dir`. That project is
retired; two of its reports are deleted and the third
(`_QA_NLI_Benchmark_Report.qmd`) is **parked** — underscore-prefixed, so Quarto
excludes it from the project entirely, and renaming it back is all that is
needed. Its metrics (Cohen's κ against human labels, the R1/R2 ceiling,
bootstrap CIs, inverse-probability weighting) are still wanted; its subject —
fine-tuned checkpoints against a zero-shot baseline — is not.
`report_project_dirs()` is back to one directory, kept as a one-element vector
so adding a second is adding an element.

**`TD_NLI_training.qmd` stays in `input/reports/`** despite being a training
design document: the main report links to it via `td_doc_link()` and the Shiny
app's TD panel lists `^TD_.*\.html$` from `output/reports/`, both of which
would silently lose it. TD docs are one family and live together.

Every report in the main project lives in one Quarto **project** — `input/reports/_quarto.yml` — rendered by `tarchetypes::tar_quarto()`:

```r
targets::tar_make(names = "report_output_dir")    # the whole report chain
targets::tar_make(names = "report_fact_checker")  # the main report + its deps
```

Three targets cover all ~34 documents, replacing **nineteen** former ones: nine that each called `quarto::quarto_render()` and then `file.rename()`d the result out of `input/reports/` into `output/reports/` (Quarto writes output next to the *input* regardless of `execute_dir`, so every one had to move its file by hand), their nine companion `*_qmd` file-tracking targets, and the old `report_output_dir`.

| Target | Renders |
|---|---|
| `reports_project` | `tar_quarto(path = "input/reports")` — the 27 generated wrapper documents plus the six `TD_*.qmd` design docs |
| `report_fact_checker` | `tar_quarto(path = "input/reports/IPBES_Fact_Checker.qmd")` — the main report, deliberately excluded from the project's `render:` list so it runs **after** the rest, since it links to and copies in their rendered html. **Its html lands in `input/reports/`, not `output-dir`** — Quarto applies a project's `output-dir` only to files it renders *as part of* the project, so a single-file render of an excluded document picks up `format:` but not `output-dir`. `build_report_output_dir()` copies it (plus its `_files/` sidecar, which matters because this is the only report with `embed-resources: false`) into `output/reports/`. Two workarounds were tried and rejected by direct test: `quarto render <file> --output-dir` is refused outright ("can only be used when rendering projects"), and re-listing the file after the exclusion in `render:` does not re-include it — the exclusion wins and the document is not rendered at all. Note also that a project render **deletes** a stray `IPBES_Fact_Checker.html` from `input/reports/`, so `reports_project` must run before `report_fact_checker`, which the qmd's own `tar_read(reports_project)` already guarantees |
| `report_output_dir` | no rendering — the deploy extras (`.nojekyll`, `index.html`, `CLAUDE.md`) that Quarto knows nothing about, plus the copy of `IPBES_Fact_Checker.html` and its `_files/` sidecar out of `input/reports/` (see `report_fact_checker` above for why that copy is unavoidable) |
| `report` | no rendering — a single entry point depending on all three, so `tar_make(names = "report")` builds the whole report chain. **`shortcut = TRUE` does not work with it**: shortcut builds only the named target and loads its dependencies from the store, so nothing re-renders. To re-render against on-disk data without walking the paid upstream, name the three explicitly: `tar_make(names = c("reports_project", "report_fact_checker", "report_output_dir"), shortcut = TRUE)`. Deliberately not `format = "file"` — `report_output_dir` already lists all ~115 MB of `output/reports`, and re-hashing it here would cost time for a duplicate of the same information |

**Why this replaced the old design.** `tar_quarto()` derives each report's dependencies from the `tar_read()` calls in the project's sources, so they no longer have to be listed by hand. The old `report_fact_checker` listed eight bare symbols and **missed five** dependencies the qmd genuinely reads (`fig_pub_per_year`, `nli_overview_figures`, `overlap_key_paper_table`, and the two `overlap_after_2018_*` tables) — those were DAG leaves, built only because a bare `tar_make()` builds everything. `output-dir: ../../output/reports` also removes the `file.rename()` step entirely, and with it the stale-`IPBES_Fact_Checker_files/libs/` bug: the main report is the only document with `embed-resources: false` (deliberate, for file size), and nothing used to move its native sidecar out of `input/reports/`.

**Parameterized reports are generated, not parameterized at render time.** Quarto renders each `.qmd` in a project exactly once, so the six families that used to be one source rendered N times with different `execute_params` are now one **shared body** (`_<name>_body.qmd`) plus one tiny **generated wrapper** per combination. The wrapper's *filename is the output filename*, so no `output_file` plumbing exists anywhere.

Two non-obvious constraints shape that design, both measured rather than assumed:

1. **Generation runs in `_targets.R`'s preamble, not in a target.** `tar_quarto()` resolves the project's file list *and* its dependency edges when `_targets.R` is **sourced** — `tar_quarto_raw()` calls `tar_quarto_files()` in its own body, and `tar_quarto_command()` computes `deps <- map(sources, knitr_deps)` there too, baking both into the target's command. A wrapper produced by an upstream target would contribute nothing on the run that created it: no source, no edge, no tracked output.
2. **The `tar_read()` calls live in the wrapper, not the body.** Quarto excludes underscore-prefixed files from the project completely — they are neither rendered nor returned by `tar_quarto_files()`, and naming them explicitly in `project: render:` does not pull them in either — so a body is never scanned for dependencies. Each wrapper therefore declares its own literally and hands the values to the body as a `report_deps` list. A side benefit: each funnel wrapper names only its own label's three targets, which is finer-grained than the old targets managed.

`tar_read_raw()` is now gone from every report. It used to be unavoidable — `IPBES_Label_Funnel_Report.qmd` computed its target name from `params$label` — and it was also invisible to `tarchetypes`, which is precisely why all six parameterized reports contributed **zero** dependency edges and each render target had to fake them with bare symbol references.

**Adding or changing a report is a `config.yaml` edit.** Each `reports:` entry names a `qmd_name`, a `title` template (`{...}` placeholders filled from that wrapper's params), and the dimension(s) to expand over — `assessment`, `granularity`, `nli_config`/`llm_config`. `label` is always derived (`REFUTES`/`SUPPORTS`), which collapsed the two former byte-for-byte twin funnel targets into a single entry. Omitted dimensions are derived, notably `nli_config` via `nli_config_for_granularity()` — the safe default, since naming the wrong config silently makes already-scored data look unscored, so a pinned value is validated against the `nli:` block and must declare the matching granularity. Generated wrappers are gitignored; `_quarto.yml` and the `_*_body.qmd` files are the real sources. Note that adding an assessment now means updating **both** `assessments:` and the relevant `reports:` entries — deliberate, since the rendered set used to be an accident of which data happened to exist on disk.

**Known gap: nothing prunes stale output any more.** The old `build_report_output_dir()` did, but it pruned by diffing the directory against a hand-maintained `expected` list which omitted `nli_training_qa_report_html` and `nli_finetuned_model_qa_report_html` — so it *deleted those two reports on every run*. Quarto's project render was measured **not** to remove files it does not manage (a stray file and a `.nojekyll` both survived one), so html from an earlier naming convention persists in `output/reports/` until removed by hand.

**The same gap covers `output/tables/`, and always has** — nothing has ever pruned that directory. Four naming generations of the funnel rds files currently coexist there (`refutes_funnel_data_GA1.rds`, `..._GA1_complete_bm.rds`, `..._GA1_bge_m3_zeroshot.rds`, `..._GA1_bge_m3_zeroshot_complete_bm.rds`), accumulated as the selected config moved from `deberta_zeroshot` to the `bge_m3_zeroshot_*` configs and as `granularity_suffix()` became unconditional. Only the name matching the current `(nli_config, granularity)` pair is live; the rest are orphans that no target reads and no target deletes. Same for the funnel html, the QA rds files and `nli_bm_explorer_<id>.html`. When judging whether something "has been built", check the filename against the *current* suffix convention rather than trusting that a plausible-looking file on disk is current.

**Manual rendering needs `--execute-dir "$(pwd)"`** (e.g. `quarto render input/reports/TD_targets.qmd --execute-dir "$(pwd)"`). Quarto executes in the document's own directory by default, which breaks both `tar_read()` (no `_targets/` there) and the relative `output/reports` paths the qmds use; `tar_quarto()` passes `execute_dir = getwd()` for you, so this only affects rendering by hand.

**Technical Design (`TD_<name>.qmd`) documents** are part of `reports_project` — each is a single self-contained file (prose plus a two-line `format:` override on top of `_quarto.yml`'s shared block), so adding one is just a new `TD_<name>.qmd` in `input/reports/`; there is no longer a `td_doc_names`/`td_doc_qmd`/`td_doc_html` chain to extend. The main report's Methods section discovers their rendered html on disk and copies it into its own `_files/` sidecar.

## Architecture

### targets Pipeline Data Flow

```
input/config.yaml
    → output/LoD/<id>.ttl                    (downloaded IPBES LOD Turtle files, gitignored)
    → output/refs/assessment=<id>/           (partitioned by assessment, gitignored)
    → output/key_messages/assessment=<id>/   (partitioned by assessment, gitignored)
    → output/zotero/assessment=<id>/         (partitioned by assessment/group id/page, gitignored)
    → output/works/assessment=<id>/km=<km>/bm=<bm>/  (partitioned by assessment/km/bm, gitignored)
    → output/snowball/nodes/assessment=<id>/     (one unified pro_snowball() run per assessment over the union of all its key papers; partitioned by assessment/relation, gitignored)
    → output/snowball/edges/assessment=<id>/     (partitioned by assessment/edge_type, gitignored)
    → output/snowball/keypaper/assessment=<id>/  (partitioned by assessment only, gitignored)
    → output/works_citing/assessment=<id>/km=<km>/bm=<bm>/       (partitioned by assessment/km/bm, gitignored)
    → output/nli_ready/assessment=<id>/km=<km>/bm=<bm>/          (work × BM-sentence cross-join; premise + bm_sentence ready for NLI, gitignored)
    → output/nli_scores/assessment=<id>/km=<km>/bm=<bm>/claim_id=<claim_id>/   (NLI SUPPORTS/REFUTES/NEI scores per citing work, gitignored)
    → output/llm_candidate_scope/assessment=<id>/km=<km>/bm=<bm>/             (per-claim citing-work match set, feeds the direct_evidence_match tag below, gitignored)
    → output/llm_relevance/assessment=<id>/keypaper=<true|false>/                (relevance score per (claim, work) pair; scored but NOT filtered on by default, gitignored)
    → output/llm_verification/scores/llm_config=<cfg>/assessment=<id>/nli_route=<route>/km=<km>/bm=<bm>/   (Phase 2 LLM review of REFUTES/uncertain NLI pairs, each pair tagged direct_evidence_match, gitignored)
    → output/tables/{refutes,supports}_funnel_{data,table_l3}_<id>.{rds,html}, output/figures/fig_{refutes,supports}_funnel_{overall,by_bm,by_bm_normalized}_<id>.png   (3-level label sieve per assessment, gitignored)

# Not currently produced (orphaned source files in R/, gitignored outputs may hold stale data):
#   output/fulltext/, output/resolved_sections/, output/sections/
```

**Active scoring approach — NLI** (`TD_BM_NLI_approach.qmd`): `nli_scores_by_claim_evidence`
classifies each citing work against its partition's Background Message as
SUPPORTS / REFUTES / NOT_ENOUGH_INFO using a zero-shot NLI model
(`MoritzLaurer/bge-m3-zeroshot-v2.0-c` — `deberta-v3-large-zeroshot-v2.0` was
the original choice, now retired; see the `nli:` comment in
`input/config.yaml` for the full switch rationale) served on a pool of RunPod
hosts (see [external/runpod/docker/nli-runpod/](external/runpod/docker/nli-runpod/), a git
submodule — see `runpod_migration_IPBES_BM_Fact_Checker/TODO_migration_runpod.md`
for the migration off this repo's own former copy). Premise = cleaned `title`+`abstract`;
hypothesis = `bm_description`. The full probability distribution is stored; all
thresholding is done downstream in `dplyr`.

**Active Phase 2 — LLM verification** (`TD_NLI_LLM_two_phase.qmd`):
`llm_verification_parquet` reviews only the NLI pairs flagged `REFUTES` or
`uncertain`, one `ellmer::chat_openrouter()` call per `(claim, work)` pair via
OpenRouter, with a resumable per-pair cache and a post-hoc check that demotes
any verdict whose cited quote isn't actually verbatim in the supplied text.
Every citing work under a claim's BM is reviewed (there is no
candidate-narrowing filter — an earlier `subset: "all"`/`"default"`
mechanism was retired once real GA1 atomic_bm data showed the narrowing
reduced routed pairs by only ~14%, not worth the lost review coverage).
Instead each reviewed `(claim, work)` pair is tagged `direct_evidence_match`:
TRUE if that citing work traces back, via `llm_candidate_scope_parquet`, to
a seed reference whose sub-chapter matches the claim's own evidence-reference
braces (supported for `naive_bm`/`atomic_bm`; always FALSE under
`complete_bm`, which has no per-sub-claim evidence tokens). Its
architecture is ported from
the sibling `Categorisation_Literature` project's LLM epistemology
classifier (`R/llm_epistemology.R` there). This replaced an earlier
truth/citing-document LLM design
(`prompts_truth_parquet` → `prompts_citing_parquet` → `alignement_scores_*`,
driven by an `analysis:` config block) that was removed outright rather than
parked — see [TD_LLM_approach.qmd](TD_LLM_approach.qmd) for that record.

The `sparql_url` key in `input/config.yaml` controls the SPARQL backend:
- `"fuseki"` — each parquet builder starts an in-memory Fuseki session on a deterministic port and POSTs the assessment's TTL into the named graph returned by `assessment_graph_iri(id)`
- Any URL — the parquet builders query that endpoint directly; no Fuseki lifecycle needed

Config is split into fine-grained targets (`sparql_url`, `workers`, `assessments_list`, `nli_active`/`nli_config`/`nli_configs_all`, `km_scope`, `granularity`, `max_length`, `claim_completion_model`, `llm_verification_active`/`llm_verification_config`) so that adding new config sections or changing one entry does not invalidate other targets. Each top-level config key maps to its own intermediate target; `nli:` and `llm_verification:` are **libraries of named `configs`** that select nothing themselves — see *Purpose blocks* below (three configs — `openrouter_cheap`/`openrouter_midtier`/`openrouter_toptier_gpt5` — carried over from the sibling `Categorisation_Literature` project's proven `epistemology:` config, including its `max_active: 24`/`max_tokens: 8000` values; see `llm_candidate_scope_parquet` below for the `direct_evidence_match` tag every config's output now carries instead of a `subset` filter).

**Per-assessment named graphs:** All three SPARQL queries wrap their patterns in `GRAPH <%GRAPH_IRI%> { ... }`. The placeholder is substituted at query time by `read_sparql_query()` in [R/extract_lod.R](R/extract_lod.R) using `assessment_graph_iri()` from [R/branch_helpers.R](R/branch_helpers.R) (currently `http://ontology.ipbes.net/report/<id>`). The same code path works against local Fuseki (TTL loaded into that graph at startup) and a shared IPBES endpoint hosting all assessments under the same IRI convention — switching backends is just a `sparql_url:` change in [input/config.yaml](input/config.yaml). If IPBES adopts a different convention, edit `assessment_graph_iri()` in one place.

### Key Design Patterns

- **targets caching**: each target is re-run only when its inputs change. Delete `_targets/` to force a full rebuild.
- **Purpose blocks**: `input/config.yaml` keeps `nli:` and `llm_verification:` as *libraries of named definitions* and puts the **selection** in a per-purpose block — `fact_checking:` and `training:`, each naming its `assessments`, `nli`, `llm` and `claim_completion`, with `training.finetune` gating the fine-tuning run. **`fact_checking:` is itself a library plus an `active:` selection** (`training:` stays flat; `purpose_config()` accepts both shapes, so this was additive): several whole configurations can be written down — "GA1 on zero-shot", "GA1 KMs A+B on the fine-tune" — and one selected. Running them all would multiply GPU and OpenRouter spend by the number of definitions, and each distinct model needs its own pod pool anyway, since `check_nli_pool_health()` stops when hosts report different models. A `fact_checking` config may also carry **`km:`**, scoping scoring to named Key Messages; **omitting it means all**, so an entry without it behaves exactly as before. GA1 has 4 KMs over 39 BMs, so naming one is roughly a 4x cut in both arms. The strings are per-assessment and inconsistent (`A.` in GA1, `KM-A1` in IAS, `KM1` in VA/TCA/BBA), matched literally, and validated inside `build_nli_claim_units()` rather than in config — KMs live in `key_messages_parquet`, a target, so config cannot check them, and `"A"` for `"A."` would otherwise enumerate zero claims and look like a successful no-op. The filter operates on the **`(km, bm)` pair**: outside GA1 a BM sits under several KMs, so filtering on `km` alone would let a shared BM leak in everywhere. **Narrowing scope computes less; it never deletes what is out of scope.** That required making three stages additive — see `consolidate_nli_scores()`, `build_llm_relevance_screen()` and `build_llm_verification_parquet()` below — each of which used to wipe its whole output subtree before writing, so a narrowed run silently destroyed every out-of-scope row. There is no global `active:` any more. "active" was a single answer to a question each project answers for itself: fact checking is scoped to `[GA1]` because it is the expensive arm, training pools all five key-paper sets, and they need not agree on a model. Resolved and **validated** by `purpose_config()` (`R/branch_helpers.R`) — naming a config that isn't in the library is a hard error, because it would otherwise read as "nothing scored yet" and re-dispatch a corpus at real GPU cost. Scope lives here rather than as per-assessment flags inside `assessments:`, which would change `assessments_list`'s value and invalidate `assessment`, `ttl_path`, `works_parquet`, `snowball_parquet` and everything downstream; `purpose_assessments_list()` deliberately preserves the exact element shape (`full_text` strip included) so a purpose listing every assessment yields a byte-identical value. Reporting resolves **both** blocks (`nli_active`/`llm_verification_active` from `fact_checking`, `nli_active_training`/`llm_verification_active_training` from `training`) — they name the same nli config today, which is exactly why keeping them distinct matters: the moment they diverge, one shared name would send half those targets to the wrong `nli_config=` directory.
- **Fine-grained config**: `config` is split into `sparql_url`, `workers`, `assessments_list`, `nli_active`/`nli_config`/`nli_configs_all`, `granularity`, `max_length`, `nli_train_enabled`, `nli_downsample_seed`, `claim_completion_model`, and `llm_verification_active`/`llm_verification_config` targets so unrelated config sections don't cascade invalidation. Note `granularity` and `max_length` are both read out of *the active nli config*, so changing the purpose block's `nli:` invalidates them together (`nli_configs_all` lives only in `_targets_reporting.R`; `nli_train_enabled`/`nli_downsample_seed` went with the training project); `nli_granularities` is a fixed literal `c("naive_bm", "complete_bm", "atomic_bm")`, deliberately **not** read from config.
- **Fuseki lifecycle**: started and stopped inside the parquet builders; cleanup is idempotent and handled by `on.exit()`.
- **Assessment branching**: `assessment` is the branch key, so adding a new assessment only computes the new branch.
- **Separated materialization**: refs, sections, key_messages, Zotero, works, snowball, works_citing, NLI scores, and LLM verification scores are all built independently; there is no cached combined `lod_data` object.
- **Parquet databases**: partitioned by assessment only, queried lazily with `arrow::open_dataset()` + `dplyr` verbs, collected into memory only when needed.
- **SPARQL queries as files**: the SPARQL queries live in `queries/*.sparql` and are tracked as `format = "file"` targets (`refs_sparql`, `key_messages_sparql`; `sections_sparql` is disabled along with `sections_parquet`) — editing a query file invalidates only its downstream parquet target.
- **Legacy QMD caching**: uses `file.exists(fn)` checks. Delete the relevant `.rds` or parquet directory to force recomputation.

### Shiny App — removed 2026-10-05

`shiny_app/` was a pure read layer over `output/` — `app.R` plus ten modules,
~1,300 lines, no target, never part of `reports_project`. Deleted on the `Jev`
branch. Verified before removal that **no function in `R/` was used only by it**,
so nothing else had to change.

Two ideas in it are worth remembering if anything like it is rebuilt. Its
dropdowns were populated by scanning `output/` at startup, **never from
`input/config.yaml`**, because the set of `(assessment × granularity ×
nli_config × llm_config)` combinations actually built is incomplete and
inconsistent with the config. And artifacts written under older naming
conventions were surfaced as `granularity = "unspecified"` rather than dropped,
so the app was the one place that showed the stale-output situation described
under *Quarto Report* instead of papering over it.

### Terminology

- **KM** = Key Message (e.g. `"A."`)
- **BM** = Background Message (e.g. `"A1"`)
- **SM** = Sub-Message
- **LOD** = Linked Open Data — IPBES assessments in RDF/Turtle format
- **key papers** = GA1 references used as snowball seeds (`oa_input == TRUE` in QMD nodes)
- **non-key papers** = papers discovered via snowball (`oa_input == FALSE`)

### Gitignored Intermediate Outputs

- `output/LoD/` — cached TTL files
- `output/refs/` — DB1 parquet (refs with Zotero group/key citations)
- `output/key_messages/` — DB3 parquet (KM, BM, and SM descriptive text with confidence flags)
- `output/zotero/` — Zotero parquet dataset partitioned by assessment/group id/page
- `output/works/` — OpenAlex works parquet dataset partitioned by assessment/km/bm
- `output/snowball/` — unified per-assessment snowball parquet datasets (one `pro_snowball()` call per assessment, over the union of every km/bm's key papers — no km/bm partitioning): nodes (assessment/relation), edges (assessment/edge_type), keypaper (assessment)
- `output/works_citing/` — **slim mapping only**: which citing work belongs to which (km, bm). One file per assessment with `km`/`bm`/`id` as columns (no km=/bm= partition tree), sorted by km/bm for row-group pruning
- `output/works_citing_meta/` — one row per *distinct* citing work (all scalar columns), partitioned by assessment. Split from the mapping because a work belongs to ~21 groups on average and duplicating full records across them came to >100 GB — see `build_works_citing_parquet.R`'s row above
- `output/nli_scores/` — NLI SUPPORTS/REFUTES/NEI scores per citing work, partitioned by assessment/km/bm (`claim_id` is a column, not a partition level)
- `output/nli_scores_evidence/` — active evidence-segmented NLI scores, same schema, partitioned by granularity/nli_config/assessment/km/bm; `<root>/.scratch/` holds per-claim files between scoring and consolidation, `<root>/.premigration/` the pre-consolidation layout kept for rollback
- `output/llm_candidate_scope/` — per-claim citing-work match set feeding the `direct_evidence_match` tag, partitioned by assessment/km/bm
- `output/llm_relevance/` — relevance score per (claim, work) pair from the Phase 1→Phase 2 screen, partitioned by assessment/**keypaper** (a real partition level, so the two chains cannot clobber each other). Scored but **not** filtered on until `relevance_screen.threshold` is set — see `R/build_llm_relevance_screen.R`
- `output/llm_verification/raw/` — Phase 2's resumable per-`(km, bm, claim_id, work_id)` JSON cache, partitioned by model/prompt hash/assessment
- `output/llm_verification/scores/` — Phase 2 LLM verification of NLI-flagged pairs (each tagged `direct_evidence_match`), partitioned by llm_config/assessment/nli_route/km/bm
- `output/llm_verification/raw_keypaper/`, `output/llm_verification/scores_keypaper/` — full-coverage key-paper LLM verification (every key paper, irrespective of NLI label/confidence); never collides with or invalidates the two above. `scores_keypaper` is partitioned by llm_config/assessment/**nli_route only** — km/bm remain ordinary columns, since nothing filters this dataset on them at the Arrow level and partitioning to km/bm produced 688 files averaging ~145 KB, mostly parquet footer overhead
